# Sipri Crypto Maintainer Guide

Sipri Crypto is a rebranded distribution of Bouncy Castle (bcgit/bc-java) built as an **overlay**. This document covers the repository layout, the upstream sync process, the rules for adding algorithms, and the evidence behind the implementations.

## 1. Principle: keep the Bouncy Castle tree identical to upstream

- Code under `org.bouncycastle` is **not modified**. Every edit to an upstream file becomes a conflict in a later merge.
- All Sipri code lives in the `sipri/` module, package `com.siprikorea.crypto` - a separate jar depending on `prov` (bcprov).
- Paths allowed to differ from upstream are listed in [`.sipri-overlay`](.sipri-overlay). CI and the sync script fail when any other path differs from upstream.

Only one upstream file is modified:

| File | Change | Merge handling |
|---|---|---|
| `settings.gradle` | one added line, `include "sipri"` | `merge=union`, keeping both sides' lines |

The `merge=union` rule is written to `.git/info/attributes` (local, untracked) rather than to the upstream-owned `.gitattributes`; the sync script and workflow add it just before merging.

The rebranded README is `.github/README.md`. GitHub shows it in preference to the root `README.md`, so the repository front page reads as Sipri Crypto without touching the upstream README.

## 2. Syncing with upstream (Bouncy Castle)

### Automatic: GitHub Actions

`.github/workflows/sipri-sync-upstream.yml` runs every Monday at 00:00 UTC (09:00 KST). It can also be started by hand from the Actions tab, with a branch or tag to merge (e.g. `r1rv87`).

1. Fetches `bcgit/bc-java`, and stops if there are no new commits.
2. Merges into the `sync/upstream` branch, based on `main`.
3. On a conflict, opens an issue labelled `upstream-sync` listing the conflicting files and the local resolution steps.
4. Otherwise runs the overlay check and `:prov:compileJava :sipri:build` (including the tests).
5. If everything passes, pushes `sync/upstream` and opens a pull request into `main`; if one is already open, the branch is just refreshed.

**Always merge these pull requests with "Create a merge commit".** A squash or rebase merge drops the upstream history from `main`'s ancestry, so the next sync merges the same changes again and conflicts.

**Token (recommended):** the default `GITHUB_TOKEN` has two limitations:
- it cannot push a commit in which upstream changed `.github/workflows/codeql.yml`;
- pull requests it opens do not trigger other workflows (Sipri CI).

Adding a fine-grained PAT as the repository secret `SIPRI_SYNC_TOKEN` fixes both. It needs Contents, Pull requests, Issues and Workflows read/write on this repository.

### Manual: `scripts/sync-upstream.sh`

```
scripts/sync-upstream.sh --check            # only report commits behind upstream and overlay drift
scripts/sync-upstream.sh --test             # merge on a sync/upstream-<date> branch, then build and test
scripts/sync-upstream.sh --test --pr        # as above, then push and open a pull request with gh
scripts/sync-upstream.sh --ref r1rv87       # merge a specific release tag
scripts/sync-upstream.sh --branch .         # merge into the current branch
```

On a conflict the merge is left in progress. Resolve upstream files by **taking upstream's version**, `git add` and `git commit`, then run `--check` to confirm the overlay is still clean.

### CI

`.github/workflows/sipri-ci.yml` runs on pushes to `main` and on pull requests: the overlay check plus the Sipri module build and tests. Upstream's `codeql.yml` is left as it is (manual runs only).

## 3. Module layout (`sipri/`)

```
com.siprikorea.crypto
├── digests      LSH256Digest (224/256), LSH512Digest (224/256/384/512), HAS160Digest
├── engines      HIGHTEngine
├── signers      KCDSASigner, ECKCDSASigner, KCDSAEncoding / StandardKCDSAEncoding, KCDSAUtil
├── generators   KCDSAParametersGenerator (TTAK procedure), KCDSAKeyPairGenerator, ECKCDSAKeyPairGenerator
├── asn1         SipriObjectIdentifiers
└── jcajce.provider
    ├── SipriCryptoProvider        provider name "SipriCrypto"
    ├── digest / symmetric         LSH, HAS-160, HMAC-LSH, HIGHT (Cipher/KeyGenerator/AlgorithmParameters/CMAC)
    ├── kcdsa                      KCDSA keys, KeyFactory, KeyPairGenerator, Signature
    └── eckcdsa                    EC-KCDSA keys, KeyFactory, KeyPairGenerator, Signature
```

Implementation notes:
- **The KCDSA public key is `y = g^(x^-1 mod q) mod p`** and the EC-KCDSA public key is `Q = d^-1 G`. These differ from DSA/ECDSA, so a DSA or EC key pair generated by another provider cannot be used as a KCDSA key pair. The signature SPIs accept the standard `DSAPrivateKey` / `ECPrivateKey` interfaces.
- Signatures are encoded as DER `SEQUENCE { r INTEGER, s INTEGER }`. Decoding is strict: input that does not re-encode identically is rejected. `r` is a hash value, so it is checked against its bit length only, not against q (or n).
- Keys are encoded with the ISO/IEC 14888-3 OIDs: KCDSA `1.0.14888.3.0.2`, EC-KCDSA `1.0.14888.3.0.5`. The Korean e-Government OIDs (`1.2.410.200004.1.1`, `1.2.410.200004.1.100.2.1`) are accepted on input only.
- HIGHT's F0/F1 are computed with rotations rather than table lookups, so no memory access depends on secret data.
- HAS-160 and HAS160withKCDSA are **legacy** features, for verifying and interoperating with existing signatures.
- Oracle JDK refuses `Cipher` / `Mac` / `KeyGenerator` from an unsigned JCE provider; OpenJDK-based JDKs have no such restriction. To use HIGHT or HMAC on Oracle JDK, sign the jar with a JCE code-signing certificate.

### Rules for adding an algorithm

1. Add the lightweight classes (`digests` / `engines` / `signers` ...) to `sipri/`. Do not modify `core` / `prov`.
2. Add the JCE SPIs under `jcajce.provider.*` and register them in `SipriCryptoProvider.setup()`. Update the service count in `ProviderTest.testAllServicesResolve` too.
3. Write known-answer tests from **published test vectors** (a standard's appendix or an independent implementation) and register them in `AllTests`. Self round trips alone are not enough.
4. Break the implementation on purpose and confirm the KAT fails (mutation check).
5. Update the algorithm tables in this document and in `.github/README.md`.

## 4. Verification evidence

| Algorithm | Test vector source | Coverage |
|---|---|---|
| LSH-224/256/384/512, LSH-512-256 | Crypto++ `TestVectors/lsh*.txt` (generated with the KISA reference implementation) | 147 each, plus incremental / Memoable paths |
| HAS-160 | TTAS.KO-12.0011/R2 samples (cross-checked against randombit.net) | 8, including one million 'a's |
| HIGHT | KISA reference code `KISA_HIGHT_{ECB,CBC,CTR}.c` (Crypto++ `TestVectors/hight.txt`) | ECB 15, CBC 8, CTR 52 |
| KCDSA | TTAK.KO-12.0001/R4 Appendix II.1-II.5 | J/p/q/g generation, y, Z, fixed-k signature (r, s) |
| EC-KCDSA | TTAK.KO-12.0015/R3 Appendix II.1-II.9 | P-224/256, B-233/283, K-233/283 with SHA-224/256 |

The KCDSA and EC-KCDSA vectors are the values [RyuaNerin/go-krypto](https://github.com/RyuaNerin/go-krypto) (MIT) transcribed from the standards, converted into `sipri/src/test/resources/.../vectors/`. Appendix II.5 prints Count as 2189, which does not reproduce p and q; the value that does is 5189.

For each algorithm, a key constant or step was altered on purpose, and the corresponding KAT failed every time.
